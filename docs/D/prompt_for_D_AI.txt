1. PROJECT OVERVIEW
================================================================================

A classroom attendance system where a student checks in by taking TWO selfies
(at the START and END of class). Attendance is GRANTED only when ALL three
conditions are satisfied:

  (1) Student's phone MAC was detected on the classroom Wi-Fi network
      (verified server-side via ARP ping sweep)
  (2) The check-in falls within the class schedule window (±15 min grace)
  (3) Both selfies match the enrolled face (InsightFace ArcFace, cosine
      similarity threshold 0.5)

If Wi-Fi fails → status `face_only` (attendance recorded but flagged).
If either face fails → status rejected (400/403/409 depending on cause).

5. STATUS FLOW & BUSINESS RULES
================================================================================

Two-stage check-in flow:
  1. Student opens app → picks schedule (or banner auto-detects)
  2. START selfie → POST /attendance/check?check_type=start
     → status = "partial" (confidence, wifi_verified shown)
  3. END selfie (same schedule) → POST /attendance/check?check_type=end
     → if Wi-Fi OK: status = "verified"
     → if no Wi-Fi: status = "face_only"

Status values (displayed in History + Dashboard):
  - "partial"    = START done, END pending (orange)
  - "verified"   = START + END + Wi-Fi confirmed (green)
  - "face_only"  = START + END done, no Wi-Fi (deep orange)
  - "present"    = alias for "verified" (green, used in dashboard)

Validation rules:
  - Check must be within class time ± ATTENDANCE_CHECK_WINDOW_MINUTES (15)
  - Wrong day_of_week → 403
  - Unknown schedule → 404
  - Duplicate check-in (same stage, same schedule) → 409
  - END without prior START → 409
  - Same photo re-used within same day (SHA-256 fingerprint) → 409
  - Photo with no face detected → 400 "Face not recognized"
  - Mac address already used by another student → 409 (anti-cheat)
  - Schedule time overlap in same room → 409

7. KNOWN ISSUES / LIMITATIONS / REMEDIATION PLAN
================================================================================

[1] Campus Wi-Fi Client Isolation
    Issue: The campus SSID uses client isolation (or VLAN splitting) —
    devices on the same SSID cannot reach each other. The ARP ping sweep only
    sees the gateway router, not individual phones. As a result, every check-in
    receives wifi_verified=false (status face_only).

    Evidence: smoke test showed laptop's own MAC as on_network=False;
    subnet auto-detects as /17 but scanner hardcoded /24 (hit only .1–.254).

    Impact: At this campus, Wi-Fi verification will NEVER work over the
    campus network. This is an infrastructure limitation, not a software bug.

    Mitigation M1: The system is designed to handle this gracefully —
    face_only status is valid. The attendance is still recorded; it is simply
    flagged without Wi-Fi confirmation.

    Planned Fix (M2): For pilot/demo, run the server on a private network
    (hotspot or home router) where ARP works. For production use, read the
    AP's management plane (SSH/SNMP) instead of ARP (identified as M2 work).

[2] Laptop Clock Drift (End-user Environment — Fixed)
    Issue: The Windows laptop clock was 8 hours behind real time (showing
    08:48 when real time was 16:48 CST). This caused every check-in to return
    403 "outside class time" because the server compared schedules against
    the wrong time.

    Fix: Manual clock synchronization. Root cause: Windows time sync failure.

    Documentation: This is a deployment checklist item — verify server clock
    before running attendance sessions.

[3] USB-Only Student Connectivity (Campus Workaround)
    Issue: Because of campus Wi-Fi isolation, the only way the student's phone
    can reach the backend is over USB via `adb reverse tcp:8000 tcp:8000`. This
    works correctly (phone URL = http://127.0.0.1:8000) but requires the phone
    to be tethered.

    Impact: Only one phone (the developer's) can be connected at a time.

    Note: The Wi-Fi check itself is NOT affected by USB path — MAC detection
    happens server-side (ARP from the laptop), not through the HTTP connection.

[4] Demo-Artifact: Gateway MAC Used for Buchari
    Issue: Buchari (test student) is registered with the campus gateway's MAC
    address (70:c6:dd:09:b0:02), not his actual phone MAC. This was done
    during initial testing to simulate Wi-Fi verification on the isolated
    network.

    Impact: On real networks, this student will always show as "on network"
    regardless of actual presence. Real pilot students must be enrolled with
    their own phone MAC.

    Fix M2: Replace with actual phone MAC before pilot.

[5] MAC Randomization (Android)
    Issue: Modern Android phones randomize their MAC address per Wi-Fi
    network. The MAC visible to ARP today may not be the same tomorrow.

    Impact: Even on a flat network, the registered MAC must match the current
    randomized MAC.

    Mitigation: Students must update their registered MAC in the app Settings
    whenever it changes. Documented behavior — not a software bug.

[6] Threshold Evaluation Sample Size
    Current: 3 students, 15 samples total, 30 genuine pairs, 75 impostor
    pairs. FAR = FRR = 0.00 across 0.25–0.65 band.

    Caveat: 3 students is sufficient for demonstration but not for production.
    The clear separation (min genuine 0.708, max impostor 0.224) suggests the
    threshold is robust, but a larger population (10+ students) would confirm.

    Recommendation: Add more subjects during pilot (M2).

[7] One-MAC-One-Student (Anti-Cheat Gap)
    Implementation: POST /students/ and PUT /students/{id}/mac reject a MAC
    already registered to another student (409, normalized comparison).

    Gap: A student could borrow another's phone (with its MAC) to gain
    wifi_verified. This is a social attack, not a technical one.

    Planned M2: Device binding via server-side authentication token.

[8] Photo Replay Guard Implementation Note
    Implementation: SHA-256 fingerprint is stored in a process-local dict
    (resets on server restart). A photo can be used once per day per student.

    Note: Cross-day reuse is still allowed. This is acceptable for the pilot
    scope. Persistent storage would be needed for production (M3).

[9] LIVE Benchmark: Campus /wifi/scan
    Result: Fresh scan takes ~2.4 seconds (ping sweep 254 addresses). Cached
    responses are instant (60-second dedupe). On the campus network, only the
    gateway was ever detected due to client isolation.

[10] Database Timestamp Inconsistency
    Issue: attendance.timestamp uses local time (TIMEZONE), while
    students.created_at and ap_logs.scan_time use SQLite CURRENT_TIMESTAMP
    (UTC). faces.created_at and schedules.created_at were also inconsistent
    but were fixed during M1.

    Status: Identified as fix candidate. Not yet resolved. Should be
    addressed before M2 to avoid confusion when reading logs across timezones.

11. DESIGN DECISIONS (for the report's "Architecture" section)
================================================================================

[1] Why two-stage (start + end)?
    To verify the student was present for the ENTIRE class, not just at the
    beginning. A single selfie at the start (or end) cannot confirm the
    student didn't leave early (or arrive late). Two stages + Wi-Fi presence
    throughout the session provide stronger evidence.

[2] Why face recognition + Wi-Fi, not just QR/barcode?
    QR codes can be shared/photographed. Face recognition ties attendance to
    an actual person present at the physical location. Combined with Wi-Fi
    MAC check, the system provides multi-factor verification:
    - Something you have (phone MAC)
    - Something you are (face)
    - Time and place constraints (schedule + AP)

[3] Why polling (GET /me/prompt) instead of WebSocket?
    WebSocket requires persistent connections and is harder to implement
    reliably across mobile network transitions. Polling every 20 seconds
    is simple, reliable, and lightweight (backend Wi-Fi scan caches ~10s,
    so 20s is safe). WebSocket upgrade is planned as Tier 2.

[4] Why threshold 0.5 and not 0.25 (optimizer's suggestion)?
    The evaluation shows 0.25–0.65 band has FAR = FRR = 0.00. Choosing the
    edge (0.25) risks false accepts with new students. The middle value 0.5
    provides maximum buffer against distribution shifts — the safety margin
    is [0.224, 0.708] = a 0.48-wide gap. Live testing on real device
    (confidence 0.893, 0.688, 0.943) confirms 0.5 works in practice.

[5] Why SQLite instead of PostgreSQL/MySQL?
    The system is a classroom-scale deployment (tens of students, one machine).
    SQLite requires zero configuration, no separate server process, and the
    entire database is a single file that can be backed up by copying it.
    Schema migrations use safe ALTER TABLE IF NOT EXISTS patterns.

[6] Why no camera bypass in auto-prompt?
    Ethics and honesty: The auto-prompt banner opens the camera — the student
    must physically take a new selfie for every check-in. No "fake" check-in
    path exists. Designed by team consensus.
