## 1. PROJECT IDENTITY

**Project name:** An Integrated Attendance Solution Merging Wi-Fi AP Data with Two-Stage Face Recognition.

**What it does:** Replaces manual university roll-call. A student logs in to a Flutter mobile app with their NIM (student ID number), takes a selfie at the START of class and another at the END. The backend verifies identity (face recognition) AND that the student's phone is on the classroom Wi-Fi network. Attendance is granted only when ALL THREE conditions are met:

| # | Condition | How it is checked |
|---|-----------|-------------------|
| 1 | Correct Wi-Fi AP | Student's device MAC address is found on the classroom network; if the schedule pins an AP (`ap_bssid`), the server's own associated BSSID must match it |
| 2 | Valid class time | Check-in within the schedule window ± 15-minute grace period (`ATTENDANCE_CHECK_WINDOW_MINUTES`), on the correct weekday |
| 3 | Two selfies matched | BOTH a `start` and an `end` check-in for the same student + schedule, each with a face that matches the enrolled face |

**Users:** students (Flutter mobile app) and teachers (web dashboard at `/dashboard`).

**LANGUAGE RULE:** ALL outputs and inputs in the project must be in English — app UI text, API responses and error `detail` strings, server logs, code comments, docstrings, identifiers, commit messages, every file under `docs/`, CSV headers, dashboard text, slides, demo video, and the final report. The two deliberate exceptions: (1) team group chat may be Indonesian; (2) work-package instruction files for members A, B, C are written in Indonesian, and instructions for D are in English — but whatever those instructions *produce* is still English.

## 3. BUSINESS RULES (ALREADY IMPLEMENTED — DO NOT REDESIGN)

### Two-stage status flow

```
start check-in  →  row inserted with status "partial"
end check-in    →  finds the "start" row, finalizes BOTH rows:
                     "verified"    = face matched AND Wi-Fi confirmed on both checks
                     "face_only"   = face matched but Wi-Fi not confirmed
```

| Status | Meaning |
|--------|---------|
| `partial` | Only the start check-in exists (waiting for end selfie) |
| `verified` | Start + end complete, face + Wi-Fi OK → attendance VALID |
| `face_only` | Start + end complete, face OK but Wi-Fi not verified |
| `present` / `pending` | Legacy values, kept for backward compatibility |

### Error responses

| Situation | HTTP code | Detail |
|-----------|-----------|--------|
| Duplicate check-in (same student + schedule + stage) | 409 | `duplicate_check_in` |
| `end` without a prior `start` | 409 | `missing_start_check` |
| Check-in outside class window ± grace | 403 | `outside_class_time` |
| Check-in on the wrong weekday | 403 | `wrong_day` |
| Unknown schedule id | 404 | `schedule_not_found` |
| Check-in not on classroom network (strict mode) | 403 | `not_on_classroom_network` |
| Overlapping schedules in same room | 409 | (create/update validation) |
| Upload too large / not JPEG/PNG / face too small | 413 / 400 | enrollment hardening |
| Multiple faces in photo (area ≥ 10% of largest) | 400 | `Multiple faces detected` |
| Face matches different student | 403 | `Identity mismatch` (no row written) |

### Strict classroom mode

- `REQUIRE_CLASSROOM_WIFI=true` → check-in from a device NOT visible on the classroom network (and, when `ap_bssid` is pinned, a server NOT on that BSSID) → HTTP 403 "You are not connected to the classroom network." No row is written.
- Off by default (`false`), which keeps the legacy `face_only` status.
- Enabled for the demo (decision D-006).
- The mobile app calls `GET /attendance/preflight` before opening the camera, so out-of-window / off-network check-ins are blocked client-side too.
- The mobile app lists only `/schedules/active` (not all schedules), removing the "pick an old schedule and take a photo" dead end.

### Face detection and recognition

- `get_embedding(image, bbox)` expects the FULL image plus the YOLO bounding box (it crops with margin internally). Does NOT take a pre-cropped face.
- Enrollment stores only the largest distinct face; rejects photos with a second face (area ≥ 10% of largest).
- Nested duplicate boxes are merged first (containment ≥ 0.6).
- `attendance.faces_detected` records the raw YOLO box count per check-in (audit column).
- `attendance.check_type` is 'start' or 'end'.

### Other verified facts

- Cosine similarity threshold: **0.5** (env `FACE_SIMILARITY_THRESHOLD`) — measured, not guessed (decision D-001).
- YOLO config: `conf 0.25`, `imgsz 640` (decision D-002, measured 3.8× faster than 1280 with identical recall on close-up photos).
- Wi-Fi scan results deduplicated per MAC for 60 seconds.
- `WI_FI_SUBNET` unset → subnet auto-detected from the machine's primary interface at scan time (real netmask, capped at one /24).
- Timestamps stored as explicit LOCAL time strings (SQLite `CURRENT_TIMESTAMP` is UTC and would break date comparisons). `TIMEZONE` env pins the zone, e.g. `Asia/Jakarta`.
- Enrollment hardening: JPEG/PNG magic-byte check, `MAX_UPLOAD_BYTES` cap (413), `MIN_FACE_BBOX_PX` filter (default 40 px), max `MAX_EMBEDDINGS_PER_STUDENT` (default 5) samples per student.
- Schedule creation/update rejects overlapping time slots in the same room (409).
- `ap_logs` is populated by `/wifi/scan` and `/wifi/check/{mac}` (60 s dedupe window).

## 4. DATABASE SCHEMA (6 tables)

- **students**: id, name, nim (UNIQUE), mac_address, created_at
- **faces**: id, student_id → students.id, embedding (BLOB, pickled), image_path, created_at
- **schedules**: id, class_name, day_of_week (0=Mon … 6=Sun), start_time "HH:MM", end_time "HH:MM", ap_bssid, room, created_at
- **attendance**: id, student_id, schedule_id, check_type ('start'|'end'), confidence, wifi_verified (0/1), status, timestamp, faces_detected (raw YOLO box count)
- **ap_logs**: id, mac_address, ip_address, bssid, ssid, scan_time (60 s dedupe window)
- **schedule_students**: schedule_id → schedules.id, student_id → students.id, enrolled_at (PRIMARY KEY = schedule_id + student_id; ON DELETE CASCADE for both foreign keys)

The `schedule_students` table was added by "Felix 22.1" (merged to main 2026-11-12) to support class-based attendance sheets with roster management. Migration: on first run after adding the table, every existing student is enrolled in every existing schedule (`INSERT OR IGNORE`).

## 8. NETWORK FINDINGS & ACCEPTED CLAIMS

### Campus network measurement (NJUPT-CMCC)
- SSID: shared across many classrooms; BSSID at test location `50:98:b8:c9:2b:e2`.
- Only the gateway visible on ARP scan — **client isolation or VLAN splitting**.
- Subnet: interface `/17` (`10.163.216.0/17`), but scan capped at `/24` (decision D-004).
- Result: student phones NOT visible → strict classroom mode would reject every check-in (403) if demo ran on campus SSID as-is.

### Demo network options (both approved by supervisor)
1. **Campus AP in the actual classroom** — preferred because BSSID proves the server is on the scheduled AP; will re-test on-site to confirm whether devices are visible.
2. **Own hotspot / portable router** — fallback if campus network isolates. SSID `Attendance-Demo`, all phones + server join, ARP scan works (measured on flat network).

### Accepted claims (supervisor confirmed)
- "The check-in was made within the coverage area of the scheduled AP" is acceptable for assessment, stated honestly.
- Supervisor's reasoning: one AP practically covers one classroom; even if signal spills to adjacent rooms, AP capacity cannot serve all students from multiple rooms simultaneously.
- What we explicitly do NOT claim: per-device AP association, RSSI-based distance, or "inside the room" — these require the AP management plane (SSH/SNMP/controller API), which we have no authorisation for. This is documented as future work in `docs/B/ap_management_plane.md`.

1. `/wifi/scan` not seeing phones → restart with `REQUIRE_CLASSROOM_WIFI=false`, demo face-only path, explain openly (sentence pre-written in `docs/B/offline_fallback.md`).

## 13. KNOWN LIMITATIONS (state these honestly in reports)

1. **No anti-spoofing / liveness detection:** `buffalo_l` cannot distinguish a live face from a photo. Mitigations: two-stage check, Wi-Fi presence, supervised classroom.
2. **Wi-Fi verification is best-effort:** ARP cache varies per router/OS; `face_only` exists because Wi-Fi can fail while the face is genuine.
3. **SQLite single-writer:** fine for one classroom/school server; not multi-school.
4. **Recognition accuracy depends on enrollment quality:** bad lighting degrades everything; threshold must be tuned on the deployment camera.
5. **AP presence ≠ device association:** We see MACs on the network segment, not which AP the phone associates to. On a multi-AP bridged network, a phone in another room could still be visible. Mitigated by one-AP-per-classroom assumption for the demo.
6. **No authenticated session:** `student_id` in the check-in API is claimed, not proven. A colluding pair could still do "buddy check-in" by sending the friend's ID with the friend's photo. Session auth is out of scope for M2, recorded for M3.
7. **Small sample size:** threshold and robustness measured on ≤5 people, not in classroom lighting. G7 pilot will expand this.
